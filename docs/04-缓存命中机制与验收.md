## 1. 输入：群聊信息特征 → 缓存约束

机制不是拍脑袋定的，逐条从群聊信息特征推出：

| # | 特征 | 对缓存机制的约束 |
| --- | --- | --- |
| F1 | 多群并行，每群独立话题 | session 隔离（02 §3）；唯一可跨群共享的是 L0 → L0 必须全群字节一致 |
| F2 | 消息流高频 append，触发（@）稀疏 | 观察路径零 LLM、零组装；**滑动/淘汰只跟回复走，不跟消息走** |
| F3 | 同一波常有多条 @ 连发 | 防抖合并为一轮（02 §4.4），一轮只产生一次 fresh 追加 |
| F4 | 消息内容异质：文本/图片/at/引用/表情 | 每类一个**冻结渲染格式**；媒体用稳定占位符；引用优先指代不展开（§2 M6） |
| F5 | 发言幂律集中（少数人占大头） | L2 top-N 档案覆盖率有上限保证，档案小而有效 |
| F6 | 静默期长，TTL 过期常见 | 静默群首轮全价是预期行为，不保温；预热默认不做（§2 M9） |
| F7 | 时间每轮变化、日期每天变化 | 瞬态只进 L4；日期类天级信息也放 L4（尾部，miss 仅自身几个 token） |
| F8 | 回复引用指向窗口内旧消息很常见 | 指代机制（§2 M6），避免同一段字节在 L4 重复出现 |
| F9 | 时钟回拨/乱序到达客观存在 | prompt 内排序按全局单调 ID，不按时间戳（§2 M5） |

## 2. 核心机制

### M0 · 统一抽象：冻结块链 + fresh 尾

整条 prompt = **冻结块序列**（各层内部也按块组织）+ **fresh 尾**（当前未冻结块 + L4）。前缀缓存对字节线性匹配，由此两条推论贯穿全部机制：

1. **尾部追加是免费的**（命中到追加点为止）→ 一切常态更新都做成"追加一个新冻结块"；
2. **中部变更使其后全部 miss**（断裂）→ 一切重写都压到最低频，并记入"断裂预算"（§2 M8）。

### M1 · 字节顺序：维持 02 的 L0→L1→L2→L3→L4

按 02 §1 定律（变化频率单调递增）推演过调换 L1/L2 的失效传播：常态下 L1 若为**追加链**（M3），其更新只影响 L1 之后字节，量级分析 L1 在前与 L2 在前的日断裂代价打平（差异 <3%）。**结论：不改 02 顺序；前提是 M3 落地。若 L1 退化为单块替换模式，则应把 L2 提到 L1 之前**（L2 天级比 L1 小时~天级更稳，L2 前置可少连累一次）。此条件写进开放问题 Q2。

### M2 · L3 分块窗口 + 水位线淘汰

- **块 = 回复间隔**：每次回复组装完成后，"上次回复以来的新消息"渲染、冻结为一个块，追加到 L3 块链尾部。块内字节永不再改（F2/F4 + docs/03 §4.2 序列化冻结）。
- **fresh 尾** = 当前进行中的块（上次回复后的新消息）+ L4。群越活跃 fresh 越大，这是信息本身的价格，不可优化，防抖（F3）只保证一轮一结。
- **淘汰只在回复组装时检查**（观察路径不碰窗口）：估算 token 超过**高水位**（默认 2000 tok 或 50 条，先到为准）→ 一次性淘汰到**低水位**（默认 40%）→ 从 L3 第一个字节起 miss 一轮（L0/L1/L2 仍命中）。
- 一次退到低水位而非逐条滑出：避免连续多轮触发淘汰、连续断裂。淘汰单位 = 整块，对齐 DeepSeek 缓存单元的"完整匹配"要求（§6）。

### M3 · L1 摘要链：append 为主，压缩为辅

- L1 不是单块，而是**冻结摘要块链** S1,S2,…：每个 compaction 产物 append 一块，每块对应一段已淘汰消息（内含消息 ID 区间标注，如"第 1-187 条摘要"）。
- compaction 由 `tasks` 队列后台执行（docs/03 §3），与淘汰解耦；产物**先落 `summaries` 表，下一次回复组装时才入链**（append 免费语义内，无需等断裂轮）。
- 链总 token 超过**高水位**（默认 800 tok）→ 整链重写为单块（低水位 300 tok）→ L2/L3 各断一轮。频率 = 天级以下，进断裂预算。
- 语义红利：分段摘要自带时间分段，比单块滚动摘要更可读；`summaries` 表天然按块存（group_id + span + text 已是 docs/03 的列）。

### M4 · L2 档案：懒更新 + 断裂窗口 flush

L2 更新使其后 L3 断一轮（约窗口大小的 miss）。原评估"等断裂轮排队"复杂度不值——但引入作息窗口（M10）后出现**确定性断裂窗口**（睡醒首轮缓存必全 miss），flush 变成一个 `if` 的成本：L2 打 dirty 标记，在睡醒轮或淘汰轮顺手提交，边际缓存代价 ≈ 0；活跃期到点若一直无断裂窗口且超 24h，直接提交兜底（避免档案无限陈旧）。

### M5 · 序列化冻结契约（渲染器规范，命中率的根基）

渲染器是纯函数：`render(冻结输入) → bytes`，同输入双渲染必须 byte-identical。所有变换在**入库时**完成，prompt 组装只做拼接：

1. **时间戳入库时渲染**为定长字符串（`MM-DD HH:MM`），prompt 侧零运行时刻计算（02 §6.1）；
2. **昵称入库时冻结**，后改群名片不改历史字节；
3. **排序按全局单调消息 ID**，不按时间戳（F9 时钟回拨免疫）；
4. 消息行定死一种格式（示例）：`[10-03 21:07] 昵称: 文本`；`[10-03 21:08] 昵称: [图片#a1b2c3]`——定界符固定、无 JSON 键序问题、比 JSON 省 token；
5. 媒体占位符 = 类型 + 内容 hash 前 6 位，同一媒体永远同一字节；
6. 渲染器带 `renderer_version`；版本升级 = 新消息用新版本渲染，**旧块字节不回改**（回改 = 全链断裂，等价事故）；
7. 组装器对 L0-L3 做逐层 SHA-256 链式 hash（`H_i = H(H_{i-1} ‖ bytes_i)`），随调用日志落库（§3）。

### M6 · 引用与媒体消解（F4/F8）

- 被引用消息**在 L3 窗口内** → 触发块只写 `[回复→#m123]`，不重复展开字节；
- **不在窗口内** → 从 `messages` 表取该消息冻结字节整行插入 L4（fresh，接受全价）；
- 图片 OCR/描述是后台任务产物，作为**新消息行**追加进当前块，永不回填历史块。

### M7 · 多群共享与 L0 发布纪律

沿 02 §3：L0 全群字节一致（F1）、git 版本化、禁止运行时生成。补充两条实现纪律：

- **启动校验**：部署时计算 L0 hash 存入构建产物；服务启动时逐 session 校验 L0 首块 hash 一致，不一致直接拒绝启动（宁可起不来，不可静默全 miss）；
- L0 改动走 git commit = 唯一合法发布通道，WebUI 热改路径在配置层禁用。

### M8 · 断裂预算（成本模型的运维化）

把"命中率"翻译成可记账的量。日断裂预算 = Σ(各类断裂单次 miss token × 日频次)。以活跃群（L3=2000、L1 链=500、L2=250，compaction 6 次/天、L2 更新 2 次/天、链压缩 1 次/天）估算：

| 断裂源 | 单次 miss | 频次/天 | 日预算 |
| --- | --- | --- | --- |
| L3 高水位淘汰 | ~2000 tok | 6 | 12K |
| L1 链 append | ~2250 tok | 6 | 13.5K |
| L2 更新 | ~2000 tok | 2 | 4K |
| L1 链压缩 | ~2250 tok | 1 | 2.2K |
| **合计** | | | **~32K tok/天** |

对照不设计时每轮全 miss（100 轮/天 × 2250 ≈ 225K），**压掉 ~85%**；且 fresh 尾与触发消息本就全价，实际节省率与 02 §5 口径一致。预算表随验收日志（§3）用真实数据重估。若 L1 append 的 13.5K 占比刺眼，调大 compaction 触发阈值即可换（摘要粒度变粗），参数在 §5。

**断裂恢复语义（预算表的读法）**：表中"单次 miss"就是断裂的全部代价——**单轮学费**。断裂轮的调用本身把新前缀整体写回缓存（官方："cache construction takes seconds"），下一轮即恢复稳态命中率；不存在"断裂后一整天低命中"的持续状态。所有设计目标都是防"每轮都断"（不设计时的状态），而非防断裂本身——单轮断裂的绝对成本在千分之一美元量级。

### M9 · TTL 与预热：默认不预热

TTL 数小时~数天且动态（§6），预热请求自身付全价写入、收益不可预测（F6 静默群常见）→ 默认不做。唯一预留：若验收数据显示"高价值群 TTL 过期后连续 3+ 轮逐步重建"成为大头，再评估"L1 入链后对活跃群发一次小 max_tokens 预热请求"。

### M10 · 作息窗口与主动插话（触发源扩展，2026-10-03 用户提出）

**作息窗口（如 8h 夜休）**：调度层硬窗口（代码判定"此刻不组装 prompt"），**不是 L0 prompt 规则**——L0 写了模型也可能违反，调度层是字节级保证；L0 可写"我有作息"作人设，但执行在代码。对缓存的净效果：

- 活跃期缓存持续被使用、不触发 TTL → 白天命中率不受影响；
- TTL 的最坏情形（回复间隔在 TTL 边缘徘徊的"间歇活跃群"）被作息**整流掉**：回复要么落在活跃期（缓存热），要么落在睡醒（接受一次全价）——随机轮盘变成**每天一次的确定性断裂**，约 5K tok/天，预算表加一行即封顶；
- 睡醒首轮 = 天然的最大断裂打包点：TTL 全 miss + 夜间积压消息大概率触发高水位淘汰 + dirty 层 flush（M4）三合一，反正都是断，一次断够，新前缀一次写好。夜间积压（哪怕几百条）全部作为睡醒轮的 fresh 进块，冻结后进前缀——"醒来知道发生了什么"的拟人叙事与机制咬合。

**主动插话（bot 根据上下文自主回复）**：对缓存是**又一触发源，语义与 @ 完全同构**——一次插话 = 一轮回复 = 一次 fresh 追加 + 窗口推进，复用同一套块链，零新机制。两条纪律：

1. 判定器用**纯规则**（关键词/热度阈值）或独立 session 的便宜模型，**不进主 prompt 链**、不改主链字节——判定调用的前缀与主链互不干扰（缓存按内容前缀匹配，不会互相清除），但主链字节纪律不可破；
2. 频率预算上限（如每小时 1-2 次）：拟人化要求（真人不刷屏）与缓存经济（回复频次 = fresh/淘汰频次）**同向**，一条参数两头收益。

**验收口径补充**：作息边界轮（睡醒首轮）与主动插话轮均如实记账；有效轮统计剔除睡醒首轮（确定性断裂，等价于 02 §7"接受首轮全价"的作息版）。

## 3. 字节稳定性验收（缓存 agent 职责之三）

### 3.1 运行时记录

`llm_call_log` 表（独立于五表骨架，随迁移建）：`ts, session_key, model, renderer_version, l0_version, layer_hashes(JSON), prompt_tokens, cache_hit_tokens, cache_miss_tokens, trigger_kind`。字段直采 DeepSeek 响应的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`（§6），不自己估算。

### 3.2 离线验收 SQL

```sql
-- 有效轮命中率（剔除每群首轮与疑似 TTL 过期轮：距上次调用 > 2h）
SELECT session_key,
       SUM(cache_hit_tokens) * 1.0 / SUM(prompt_tokens) AS hit_ratio,
       COUNT(*) AS rounds
FROM llm_call_log c
WHERE (ts, session_key) IN (...)  -- 落地时按窗口函数改写
GROUP BY session_key;
```

```sql
-- 断裂源定位：与同 session 上一轮逐层比对 hash，第一个变化层即断裂点
-- 离线脚本按 layer_hashes JSON 做，SQL 仅粗筛 miss 突增轮
SELECT ts, session_key, cache_miss_tokens, layer_hashes
FROM llm_call_log
WHERE cache_miss_tokens > 1000
ORDER BY ts DESC LIMIT 50;
```

### 3.3 单测清单（字节稳定性 gate，CI 可跑）

1. 渲染确定性：同一 `messages` 样本双渲染 byte-identical；
2. L0 跨群一致：任意两个 session 组装出的 L0 段 hash 相同；
3. 无运行时刻泄漏：L0-L3 字节中不出现组装时刻/日期字符串（正则断言）；
4. 块冻结：回复后回放组装，历史块字节与上轮日志中的逐层 hash 一致；
5. L0 hash 与构建产物记录值一致（M7 启动校验的单测版）。

### 3.4 验收阈值

活跃群（两次回复间隔 <2h）有效轮命中率：**≥85% pass；80–85% 观察；<80% 必须按 3.2 定位断裂源并归因**。归因预期：淘汰轮与 L1 入链轮是合法断裂，其余均为 bug（渲染抖动、顺序错误、L0 变更）。

## 4. 实现锚点（AstrBot 侧）

- **接管方式（改写式）**：插件 `@filter.on_llm_request()` 钩子重写 `req.system_prompt`（L0-L2）+ `req.contexts`（L3 块链消息数组 + L4 触发块）。参考实现：astrbot_plugin_deerpipe（最小钩子）、astrbot_plugin_connectome（含 `/llmhook debug` 载荷打印，验收期直接抄）。
- **persona 不复用**（回应 02 §7 结构开放问题第 1 条）：AstrBot 的 persona 存 DB、WebUI 可热改，直接违反 L0 git 冻结纪律 → L0 唯一合法来源是仓库文件，组装器忽略 persona 配置；AstrBot 收敛为"平台接入 + 事件流层"（02 §7 倾向方向的落地）。
- **首要风险——双历史源**：AstrBot 自带 `conversations` 表会向 `req.contexts` 注入历史（02 §7 第 2 条）。组装器**必须清空/旁路自带历史**，否则分层被未知字节污染、全盘 miss。实现首日就写断言：钩子入口处 `req.contexts` 若非空则记日志并覆盖。
- 观察路径与组装器共用 `messages` 表读取接口；组装器不写库（写方在持久化管道），单向依赖。

## 附录 A · 端到端走查：100+ 条群消息 + 一次 @

**前置状态**（昨天最后回复后）：L0=角色卡 v5（内存，hash 已校验）；L1=摘要链 [S1,S2,S3] ≈500 tok；L2=top5 档案 ≈250 tok；L3 冻结块 [B10,B11,B12] ≈1500 tok；此后群里陆续 100+ 条新消息 ≈2000 tok——只在 `messages` 表，未进过任何 prompt（进行中块）。

| 时机 | 读 | 写 |
| --- | --- | --- |
| T0 观察路径 ×100+ | 无 | `messages` +1 行/条（canonical_line 冻结字节、昵称冻结、媒体占位符）；含图片则 media 任务入队；零 LLM、零组装、不碰缓存 |

**角色形象（L0）**：全程零改动——L0 是 git 冻结文件，只读；"你以后叫我 X"类偏好写进 L2（档案）或 L1（摘要），永远不回写 L0。
**用户形象（L2）**：本轮只读（渲染进 prompt）；更新是 T4.5 的后台懒动作，不在回复路径现算。
**DeepSeek 侧**：100 条消息只付一次全价（本轮 fresh），本轮连同新前缀写入缓存；下一轮起进前缀享 1/5~1/10 命中价，直至 TTL 过期或随块滑出窗口。

## 1. 设计原则

DeepSeek 上下文缓存**全自动**、按前缀匹配（64 token 粒度）、命中价 ≈ 未命中的 1/10、小时级 TTL。没有手动断点机制，**唯一杠杆是 prompt 的组装方式**。

核心定律：**prompt 按"变化频率单调递增"分层排列；失效永远落在便宜的后缀，昂贵的稳定前缀不动。**

## 2. 分层定义

| 层 | 内容 | 变化频率 | 缓存语义 |
| --- | --- | --- | --- |
| **L0** | 角色卡 + 全局行为规则 + 工具说明 | 周/月级 | 所有群共享同一份字节 |
| **L1** | 本群摘要 / 群记忆（compaction 产物） | 小时~天级 | 后台预消化，不在回复路径现算 |
| **L2** | 本群活跃用户档案（top-N） | 天级 | 低频懒更新，接受短暂过期 |
| **L3** | 原始消息滑动窗口（条数 + token 双上限） | 每条消息追加 | 只有头部滑出才失效 |
| **L4** | 触发消息 + 瞬态信息（如当前时间） | 每轮 | 唯一真正的全价 token |

## 3. 多会话语义

- session key = 群号；每群一条独立 prompt 链，L1/L2 各群隔离。
- **红线：群相关内容（群名、群规）禁止进入 L0**。L0 全群字节一致 → DeepSeek 按账号+前缀匹配，群 A 缓存的 L0 群 B 直接复用。
- L0 走 **git 版本化**（仓库内文件，部署时冻结）；WebUI 热改角色卡 = 全部群缓存失效一次，属事故级操作。
- 实现锚点：session key 用 AstrBot 的 `unified_msg_origin`（platform:message_type:session_id），群消息取 `event.get_group_id()`（非群返回空串）；事件字段清单见 docs/01 §5。

## 4. 回复路径与预消化（@ 大上下文的消解）

1. **被动观察（零 LLM）**：群里每条消息只写 `messages` 表，不推理。
2. **预消化（廉价低频）**：后台任务把滑出 L3 的旧消息压成 L1 摘要、更新 L2 档案；节奏独立于 @ 频率；用便宜模型或纯规则（待定）。
3. **回复组装**：@ 到达 → prompt = L0…L4。L0~L3 绝大部分是缓存前缀，全价 token 只有触发消息 + 窗口尾部新增。
4. **防抖**：短时间多条 @ 合并为一次调用。

## 5. 成本模型

设稳定层 2.5K tok、每轮 fresh 500 tok：不设计 = 3K 全价/轮；设计后 ≈ 500 + 2500×0.1 = 750 tok 当量，**省 75%**；窗口 6K 时省 90%+。缓存命中同时压低首 token 延迟。

## 6. 命中率杀手清单（实现验收用）

1. system prompt 嵌时间/日期 → 每轮全 miss。时间放 L4 或不给。
2. 每次回复"重新格式化"历史（时间戳格式/排序抖动）→ 全量 fresh。**消息入库即序列化冻结**（与 docs/03 纪律 §4.2 互为因果）。
3. 档案更新插 prompt 中间 → 更新点后全 miss。L2 低频更新 + 放 L3 之前。
4. 角色卡改一个标点 → 全群 L0 失效。L0 走 git，改动即事件。
5. 静默群 TTL 过期后首轮全价 → 预期行为，不保温。
6. 多实例/灰度时 L0 字节不一致 → 部署即冻结，禁止运行时生成 L0。

## 7. 参数待定

| 参数 | 默认草案 | 说明 |
| --- | --- | --- |
| L3 窗口 | 50 条 或 2000 tok，先到为准 | 影响成本体感最大 |
| L1 compaction 触发 | 窗口溢出即触发，后台消化 | 决定摘要更新频率 |
| L2 top-N | 5 用户 × ~50 tok/人 | 档案字段 schema 见 docs/03 |
| 预消化执行者 | 待定：便宜模型 vs 纯规则 | 影响成本与摘要质量 |
| 唤醒条件 | 仅 @ | 唤醒词/主动插话后议 |
| 静默群 TTL 策略 | 接受首轮全价 | 不做保温 |

**结构开放问题（2026-10-03 调研后立，优先级高于参数表）**：AstrBot 自带会话管理——`conversations` 表存 LLM 线程历史（**2026-10-04 修正：逐次立即提交**，原"60s 批量落盘"说法已被 docs/01 §5 晚④源码核实推翻，60s 只是遗留字段 `save_interval`；对缓存设计无影响，"写库即定字节"语义反而更稳）、`persona_id` 挂人格。L0-L4 自管组装要在哪个点接管它？两个具体张力：

1. **L0 若复用 AstrBot 的 persona 机制**：persona 经 WebUI 可热改、存 DB——直接违反"L0 git 版本化、部署时冻结"纪律；
2. **L3 若交给 AstrBot 内置历史拼接**：前缀的字节稳定性不受我们控制（杀手清单第 2 条）。

倾向方向（待缓存 agent 出方案确认）：**插件层全量接管 prompt 组装**，AstrBot 只当平台接入 + 事件流层；persona 与历史全部走我们自己的库与文件。

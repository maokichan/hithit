## 1. 定位

OneKichan 是动平衡的退行产物：**群聊是薄皮，底下按情报工具需要的底座来建**。`messages` 表既是群聊的地基，也是未来情报工具的原料——这是全设计的支点。逐代迭代的工具是项目的真实焦点；"退行"不是删底座，而是先只长出 chat 这一层。

## 2. 存储选型

- **单 SQLite（WAL 模式）**，落 `/home/onekichan/data/`（变体 C 通过后）。
- 不引入 Redis / Postgres：单用户 bot 的高并发组件属过度设计。
- 大产物（工具输出、媒体）落盘 + DB 存指针，不塞库。

## 3. 核心表（五表骨架）

| 表 | 语义 | 关键点 |
| --- | --- | --- |
| `messages` | **append-only 观察流**：所有群消息（含未触发回复的） | 群聊地基 = 情报原料；schema 从宽（content 用 JSON）；⚠️ AstrBot 自带 `platform_message_history` 表也存原始消息，边界见 Q5 |
| `summaries` | L1 物化（docs/02） | group_id + span + text + token 数 + version |
| `user_profiles` | L2 物化 | 低频懒更新，字段 schema 待 agent 草案 |
| `tasks` | 任务/作业队列 | kind, payload, status, scheduled_at, result；**摘要生成是第一个消费者**，未来工具任务共用此骨架 |
| `tool_runs` | 工具调用账本 | tool, args, status, artifacts_path, error；产物落 `data/tools/<run_id>/` |

**分阶段**：一期实现 `messages` + `tasks`（摘要用）+ 两个物化表；`tool_runs` 建表占位。动平衡能力以后往 tasks/tool_runs 上长，schema 不迁移。

## 4. 数据生命周期（保留按属性分级，2026-10-03 与用户对齐）

原则：**"是否落盘、留多久"是逐类设计决策，不做"全量保留"默认假设**；容量是生命周期的下游结果，不是选址的第一因。写入纪律（append-only）与保留周期（TTL 淘汰）是两条正交的轴。

| 级 | 数据 | 保留策略 | 备注 |
| --- | --- | --- | --- |
| T0 | 群图片/语音/视频 | **几乎不落盘**：消息库只存引用元数据（类型/文件 ID/尺寸）；需要视觉或转写时按需拉取 → 用完即弃；仅显式标记的进 T5 | 容量大头直接消灭 |
| T1 | 原始文本消息流 `messages` | 热层全量（草案 90 天）；到期时摘要已沉淀，原文清除或压缩归档 | **唯一不可重建的层**——保留期 = §6 Q3，用户拍板 |
| T2 | 摘要 / 用户档案（物化层） | 长期保留（文本量小） | 依赖 T1 重建 → T1 保留期 ≥ 重建需要 |
| T3 | LLM 会话线程 | 滚动窗口自然淘汰，不额外归档 | AstrBot 自带或自管，量小 |
| T4 | tasks / tool_runs | 元数据长期（小）；**工具产物按工具单独定周期**，默认短保留 | 动平衡侧通配项，别让它成为第二个无限增长点 |
| T5 | 显式保留媒体 | 用户/群成员明确要求记住的图、文件 | 例外通道，量小 |

体量推论：文本为主 + 媒体不落盘 → 稳态几十~几百 MB/年量级 → **容量降级为次要约束**（docs/01 D5 已随之修正），存储位置可瓶颈驱动再议。

## 5. 开发纪律（硬约束）

1. `messages` 只追加：UPDATE/DELETE 视为 bug。仅有的两个例外通道都必须显式、留痕：用户行使删除权；按生命周期策略的批量清除（§4——append-only 是写入纪律，与保留周期正交，TTL 清除不是违规）。
2. **序列化冻结**：消息入库即定字节，docs/02 的缓存命中依赖这一点。
3. **可重建性**：派生数据必须能从 `messages` 热层重建，重建脚本是一等公民、随代码走。⚠️ T1 原文过期清除后，派生层（T2）即为主副本、不可再生——这正是 T1 保留期要慎重拍板的原因（§6 Q3）。
4. SQLite 写入中禁裸 `cp`；备份用 python `sqlite3` 模块的 `Connection.backup()`（**2026-10-04 修正：本机无 sqlite3 CLI**——`sqlite3.connect(dest)` 作为目标连接传入 `src_conn.backup(dest_conn)` 即可，与 `.backup` 命令等效且在线安全），每日一份保 7 天；媒体缓存可丢弃、不进备份。
5. schema 变更走迁移文件（版本号递增），禁止手改现库。
6. 每次工具调用必记 `tool_runs`；工具产物先落盘、DB 记指针。
7. 凭据（API key）不进库不进 git；`chmod 600`，走 EnvironmentFile 注入。
8. **数据根目录单一化**：一切存储路径从一个数据根配置派生——存储位置是**部署参数**而非架构承诺。这是"遇到瓶颈再迁移也来得及"成立的工程前提：迁移 = 停机 + rsync + 改一个值。
